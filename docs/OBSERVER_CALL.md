# Пробный звонок наблюдателя

Откройте **http://localhost:8090/registrar** без пароля и нажмите «Начать пробный звонок». Ответ помощника звучит в 48 кГц. Нажмите «Говорить», произнесите вопрос и нажмите «Остановить и отправить»; запись автоматически завершится через 11 секунд. Рядом появятся распознанная фраза, текущий шаг и выбранный маршрут. Во время разговора дерево архивного сценария скрыто. После завершения нажмите «Закончить просмотр», чтобы вернуть его.

Для голосового звонка запустите весь стенд с локальными моделями и NVIDIA GPU:

```bash
./clinic start --gpu
```

`./clinic start editor` запускает только редактор. Для микрофона и ответа нужны доступные модули ASR и TTS: адреса задаются администратором через `ASR_URL` и `TTS_URL` в окружении редактора. Без них звонок покажет ошибку модуля. Браузер разрешает микрофон на `localhost` и HTTPS; при отказе в разрешении можно продолжить клавишами.

Три категории: участковый терапевт или педиатр, врач-специалист, исследования или анализы. Специализацию называют голосом. Порядок направлений взят из [регламента, раздел 2.3](requirements/clinic-regulation.txt): хирург, офтальмолог и ЛОР доступны напрямую, кардиолог и ряд других специалистов — по направлению; исследования и анализы — по направлению. Без направления предлагается сначала участковый врач. Возможность платной диагностики упоминается в регламенте, но этот короткий пример её не оформляет.

Голос и клавиши работают в одном разговоре. Цифры в меню выбирают только три категории; отдельного меню с кнопками каждого врача нет. На вопрос о направлении `1` означает «да», `0` — «нет», `2` — помощь регистратора. `*` просит регистратора, `#` возвращает в начало. Внутри выбора специалиста `0` просит помощь регистратора.

Это проверяемый тестовый разговор с отдельной SQLite. После выбора врача требуются ФИО, дата рождения, проверка карточки, направления и свободного талона, выбор времени и финальное подтверждение. Только после этого создаётся строка в тестовой таблице; настоящая МИС не меняется. Текст сохраняется после каждого шага, звук — только с галочкой согласия.

Админка содержит настройки модулей, журнал звонков, граф фактического маршрута и таблицы параметризованных запросов. Поддерживается ввод текста и импорт разговоров сотрудника с пациентом. Полный текущий контракт и ограничения: [ADMIN_MODULES_CALLS.md](ADMIN_MODULES_CALLS.md).

API тестового разговора: `POST /api/demo-call/start`, `/audio`, `/text`, `/dtmf`, `/inspect`, `/end`; `GET /catalog`. Случайный call_id связан с клиентом и действует 15 минут; архив после завершения остаётся в editor-data. Изменять настройки и просматривать общий архив/таблицы может только администратор. Обычный посетитель не получает доступ к чужим звонкам.

## Проверка

```bash
PYTHONPATH=runtime/src python -m pytest -q -o addopts='' \
  --basetemp=debug/runs/observer-call/pytest-temp \
  tests/integration/test_demo_call.py tests/integration/test_demo_call_http.py

EDITOR_URL=http://localhost:8090 EXPECT_CUDA=1 \
OUT_DIR=debug/runs/local-gpu/speech-ui/hosted \
node debug/run_observer_call.mjs

EDITOR_URL=http://localhost:8090 EXPECT_CUDA=1 \
OUT_DIR=debug/runs/local-gpu/speech-ui/hosted-voice-only \
node debug/run_observer_speech.mjs
```

Браузерный прогон генерирует настоящую тестовую фразу пациента, подаёт WAV как микрофон Chrome и пропускает его через обычную запись браузера и настоящую ASR. Это позволяет воспроизводимо проверить микрофонный тракт; непосредственный пользовательский тест со своим физическим микрофоном выполняется теми же кнопками.

Браузерный runner проверяет клавиши без микрофона и совместный голосовой/тональный маршрут. Отдельный `run_observer_speech.mjs` проходит весь разговор только речью: офтальмолог → полные ФИО → дата рождения → свободный талон → финальное подтверждение, без единого DTMF-запроса. Для него настоящая TTS создаёт WAV, который передаётся настоящей ASR. Артефакты находятся в `debug/runs/observer-call/`: входная фраза `01-patient-cardio-microphone-48khz.wav`, фактическая запись браузера `04-browser-recorded-microphone.wav`, `signal.json` с RMS/частотой/длительностью, `browser-result.json`, журналы и скриншоты настольного/мобильного интерфейса. Успех включает реальное воспроизведение аудиоплеером, выбор кардиолога по распознанной речи, скрытие архивного дерева на время звонка и его возврат после закрытия, запрет изменений сценария анонимным клиентом.

Последние результаты из `debug/runs/observer-call/` получены 17.10.2026 в нативном стенде. Они проверяют настоящую речь, но не подтверждают GPU внутри Docker или работу физического микрофона пользователя. Повтор размещённой версии с CUDA ASR сохраняется отдельно в `debug/runs/local-gpu/speech-ui/`; при `EXPECT_CUDA=1` браузерный runner требует фактические `recognized.provider=CUDAExecutionProvider` и `cuda_verified=true`. Аппаратное выполнение CUDA доказывается также профилями ASR, а не названием браузерного теста.

Проверка Docker 18.10.2026: оба runner прошли с `EXPECT_CUDA=1`. Chrome воспроизвёл ответ 48 кГц; записанный через микрофон WAV прошёл настоящую CUDA ASR, выбрал кардиолога; отдельно прошли клавиши без ASR и смешанный маршрут. Voice-only завершил три речевых шага без DTMF. В каждом ответе ASR сохранены `CUDAExecutionProvider` и `cuda_verified=true`. Скриншоты `hosted/02-observer-call-welcome.png`, `06-mobile-linear-dialogue.png`, `07-archive-restored.png` просмотрены: дерево скрыто на время демо, возвращается после закрытия, на мобильном нет горизонтального переполнения. Это проверка Chrome с WAV как микрофонным устройством; физический микрофон пользователя отдельно не проверялся.
